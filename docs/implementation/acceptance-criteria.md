# معیارهای پذیرش — Acceptance Criteria

> مرحله ۱ — ۲۰۲۶‑۱۰‑۱۴
> هر معیار **قابل اندازه‌گیری و قابل تست** است و روشراستی‌آزمایی آن مشخص شده. معیارهایی که هنوز قابل اندازه‌گیری نیستند صریحاً با `[نیازمند baseline]` علامت خورده‌اند تا در اجرا با داده واقعی کالیبره شوند.
>
> قواعد عمومی:
> - «تست سبز» یعنی اجرای واقعی و ثبت خروجی (تعداد پاس/شکست/اجراننشده) در گزارش مرحله — نه ادعا (قانون ۱۲).
> - هر معیار شکست‌خورده باید یا اصلاح شود یا با دلیل مستند در `docs/limitations.md` به‌عنوان محدودیت پذیرفته‌شده ثبت شود.

## ۰. معیارهای پذیرش سطح محصول (برای کل پروژه)

| # | معیار | روشراستی‌آزمایی |
| --- | --- | --- |
| G1 | هیچ دسته اصلی از منابع بدون بررسی نمانده باشد: همه ۱۶ دسته درخواستی + دسته‌های کشف‌شده در کاتالوگ حضور دارند و هر کدام `DISCOVERED/INACCESSIBLE/NOT_CHECKED` با دلیل دارند | بررسی `source-catalog.md` + تست unit که برای هر `SourceCategory` حداقل یک `CoverageRecord` با دلیل غیرتهی وجود دارد |
| G2 | هیچ قابلیت غیرقابل دسترسی به‌عنوان پیاده‌سازی‌شده معرفی نشود | تست snapshot روی متن UI/گزارش‌ها + بازبینی اینکه هر `BLOCKED/REJECTED` در `limitations.md` ثبت شده |
| G3 | هر رکورد زمانی یا `DateKind` رسمی دارد یا `derivation` | تست DB constraint + unit test؛ شمارش رکوردهای `ESTIMATED` بدون derivation باید **صفر** باشد |
| G4 | هیچ رازی (رمز/توکن/کوکی/secret) در DB، لاگ، export یا Git نباشد | ۷ تست دروازه‌ای `security-model.md` بخش ۵٫۳ + secret‑scan در CI |
| G5 | اپ کاملاً آفلاین (بدون هیچ اتصال) حداقل ۴ منبع داده واقعی ارائه دهد | تست دستی روی emulator با airplane mode: packages, permissions, imports (MBOX/CSV/password export) |
| G6 | هر عملیات طولانی قابل ادامه از نقطه توقف باشد | تست «kill process وسط اسکن/import» و «قطع شبکه در صفحه N» → ادامه از آخرین cursor بدون داده تکراری |
| G7 | پیشرفت همه عملیات طولانی قابل مشاهده باشد | تست UI: نوار پیشرفت + `tasksDone/tasksTotal` + اعلان؛ هیچ حالت «بی‌خبر» نباشد |
| G8 | گزارش پوشش صادقانه تولید شود و هرگز ادعای کامل‌بودن نکند | snapshot test روی متن‌ها + بررسی نبود عبارت‌های مطلق («همه حساب‌ها») |
| G9 | حذف داده در ۵ سطح کار کند و قابل اثبات باشد | تست: پس از L4، dump DB + files + Keystore → صفر رکورد؛ `AuditLog` ثبت شده |
| G10 | تست‌های واحد، یکپارچه‌سازی و UI واقعاً اجرا شوند | CI workflow با jobهای مجزا + گزارش پوشش کد |
| G11 | پوشش کد `core:*` و `parsers/*` ≥ ۸۰٪ (branch ≥ ۷۰٪) | JaCoCo/Kover در CI (بلوکه‌کننده) |
| G12 | هر connector جدید قبل از merge، contract test مشترک را پاس کند | CI job `connector-contract-test` |
| G13 | RTL و سه زبان fa/en/de کامل باشد | تست UI با localeهای مختلف + screenshot test |
| G14 | زمان سرد-شروع تا اولین داده مفید ≤ ۱۰ ثانیه روی دستگاه میان‌رده | Macrobenchmark `[نیازمند baseline در P11]` |
| G15 | import آرشیو ۲GB بدون OOM و با مصرف اوج حافظه ≤ ۲۵۶MB | تست instrumented + `androidx.benchmark` `[نیازمند baseline]` |

## ۱۲. روش گزارش‌دهی نتیجه تست‌ها (اجرای قانون ۱۲ و ۱۵)

در پایان هر فاز، گزارش با این قالب در `docs/reports/phase-P<N>-report.md` ثبت می‌شود:

```
# گزارش فاز P<N>
- بازه: <تاریخ شروع> تا <تاریخ پایان>
- فایل‌های تغییرکرده: <تعداد + فهرست مهم>
- قابلیت‌های تکمیل‌شده: <فهرست با ارجاع به معیارهای پذیرش>
- تست‌های اجراشده: <دستور دقیق> → پاس: X، شکست: Y، اجرا‌نشده: Z
- موارد تست‌نشده و دلیل: <فهرست صادقانه>
- خطاهای باقی‌مانده: <فهرست با severity>
- محدودیت‌های فنی کشف‌شده: <ارجاع به limitations.md>
- معیارهای پذیرش شکست‌خورده: <فهرست + تصمیم: اصلاح / پذیرش مستند>
- کامیت‌ها: <shaها> + وضعیت پوش
- دستور ادامه مرحله بعد: <جمله دقیق>
```

هیچ فازی بدون این گزارش «تمام» حساب نمی‌شود.
